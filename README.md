# Нефтекод 2026 — мультиагентная система поддержки решений

Цепочка **АВТ → гидроочистка → блендинг**. Система читает состояние процесса из
телеметрии и доступных анализов, оценивает последствия возможных изменений режима и
выдаёт оператору безопасную объяснимую рекомендацию — либо **отказывается**, когда
надёжного решения нет.

Работает на реальных данных пакета: 189 217 десятиминутных точек с 01.01.2023 по
07.08.2026, лабораторные анализы, поточные анализаторы. Решение — 9 мс, сборка
состояния — 4 мс.

Ядро — установка **24-2000** (гидроочистка). АВТ входит как свойства сырья и возмущения,
блендинг — как балансовая модель смеси. Обоснование области — `CLAUDE.md` §3.

## Быстрый старт

```bash
pip install -r requirements.txt
pip install -e .
```

Python ≥ 3.11. Дальше — три шага; первые два делаются один раз.

**1. Кэш из сырых файлов.** Положите в `data/raw/`:

```
242000_tags.csv                 телеметрия установки 24-2000
ЛИМСы 01.01.2023 - н.в_.xlsx    лабораторные анализы
Выгрузка ПАК 01.01.2023 - н.в_.xlsx   поточные анализаторы
```

```bash
python -m scripts.build_cache
```

Пишет `data/cache/*.parquet` — примерно 11 секунд. Кэш это **сырой разбор**: значения-
заглушки не сняты, чистка живёт в одном месте (`scripts/realdata.py`). Ниже по течению
никто и никогда не читает `data/raw/`.

**2. Модели.** Коэффициенты, а не пиклы: обучение офлайн, в боевом пути только numpy.

```bash
python -m scripts.analysis.labels
python -m scripts.analysis.quality_baseline_fit
python -m scripts.analysis.breach_classifier
python -m scripts.analysis.reliability_reference
python -m scripts.analysis.economics_reference
python -m scripts.analysis.blend_components
```

Каждый скрипт пишет по файлу в `models/` и печатает, на чём обучался. Вся
последовательность — около 1.5 минуты. Порядок важен: метки нужны всем остальным.
Готовые коэффициенты лежат в git, так что шаг можно пропустить — он нужен, чтобы любое
число в системе можно было пересчитать из исходных файлов.

**3. Решения на реальных данных.**

```bash
python -m scripts.run_real --week risk
```

Печатает сводку недели и карточки, пишет по JSON-трассе на каждое решение в
`artifacts/real/`. Одна метка времени:

```bash
python -m scripts.run_real --at "2026-07-18 16:00" --all-cards
```

**Консоль оператора:**

```bash
streamlit run ui/app.py
```

**Ноутбук со всем пайплайном** — `notebooks/neftecode_pipeline.ipynb`: 13 разделов от
сырых файлов до карточки оператора, исполняется целиком за 130 секунд с переобучением всех
моделей. В первой ячейке есть `RETRAIN = False` — тогда берутся готовые коэффициенты из
`models/` и прогон заметно короче.

**Тесты:**

```bash
pytest
```

## Как устроен один цикл решения

```
data/raw/  ──build_cache──▶  data/cache/*.parquet
                                      │
scripts/analysis/*  ──▶  models/*.json│
                             │        ▼
                             │   ProcessState           снимок, окна, ЛИМС и ПАК
                             │   на момент t            с возрастом каждого анализа
                             │        │
                             ▼        ▼
                   ┌─────────┴────────┴──────────┐
                   │  агент качества             │  сера, интервал, риск нарушения
                   │  агент надёжности           │  тяжесть режима, катализатор
                   │  агент смеси                │  серный бюджет резервуара
                   └──────────────┬──────────────┘
                                  │
                   оптимизатор  ◀─┴─▶  жёсткие ограничения
                   9 кандидатов         сера по p95, диапазоны, доли
                                  │
                             оркестратор          проверка данных, конфликт целей
                                  │
                   ┌──────────────┴──────────────┐
                   ▼                             ▼
            трасса JSON                  консоль оператора
            на каждое решение            карточка из 7 блоков
```

Исходов ровно три: **рекомендация**, **удержание режима**, **отказ**. Поле
`audit.decision.outcome` в трассе принимает значения `recommend` / `hold` / `refuse`.

**Обмен между агентами виден в коде, а не только на схеме.** Три примера:

- агент смеси считает **серный бюджет** — сколько серы в гидроочищенном ДТ резервуар
  доведёт до нормы товарного продукта — и оркестратор создаёт жёсткие ограничения на
  этот цикл с этим лимитом. Гидроочистка сама знать этого не может: запасы компонентов
  находятся за пределами установки;
- агент надёжности отдаёт оптимизатору **границы рычагов**, и они не совпадают с
  конфигурационными: текущий режим допускается с запасом в один шаг за исторический
  диапазон, а сдвинутый рычаг должен попасть внутрь;
- жёсткая проверка серы читает **верхнюю границу интервала** агента качества, а не его
  точечный прогноз.

## Откуда берутся данные и как это работает непрерывно

**Сейчас** данные приходят файлами: `data/raw/` → кэш → `RealStateBuilder.build(t)`.
Построитель даёт **гарантию как-если-бы**: на момент `t` он возвращает только то, что было
доступно в `t`. Лабораторный анализ становится видимым через 4 часа после отбора пробы
(подтверждено организаторами), окна признаков заканчиваются в `t`, состояние катализатора
считается только по полным суткам до `t`. Это единственное место, где возможна утечка из
будущего, и поэтому единственное, которое проверяется тестом.

**Непрерывный режим** — тот же код в цикле:

```bash
python -m scripts.run_real --follow --week risk --tick 2
```

Решение каждые `--tick` секунд, карточка печатается при смене решения, трасса пишется
сразу. Построитель создаётся один раз и переиспользуется: инициализация 446 мс, дальше
4 мс на состояние и 9 мс на полный цикл. При темпе организаторов (15–60 минут между
решениями) это 0.001 % времени, то есть производительность здесь не является вопросом.

**Что меняется при переходе на промышленные данные — один слой.** Вместо CSV и xlsx
построитель состояния читает теги из системы истории АСУ ТП, анализы из лабораторной
системы, показания поточных анализаторов и запасы компонентов из планирования. Агенты и
оркестратор не меняются вообще: они чистые функции от `ProcessState`, без файлов, сети,
обращений к часам и глобального состояния.

**В консоли нет и не нужно путей для загрузки данных.** Консоль — просмотрщик трасс.
Если дать ей загружать данные самой, она начнёт дублировать пайплайн, и один и тот же
момент сможет дать разные ответы в консоли и в скрипте. Воспроизводимость важнее удобства.

## Демонстрация: четыре периода

Все четыре взяты из отложенной части данных (после 12.09.2025 14:30). 168 решений на
неделю, раз в час.

| Команда | Период | Что показывает | Итог |
|---|---|---|---|
| `--week stable` | с 25.01.2026 | система **не создаёт** лишних действий | 99 % удержание |
| `--week risk` | с 12.07.2026 | риск ухудшения качества, система **действует** | 68 % удержание, 32 % рекомендация |
| `--week degraded` | с 02.07.2026 | установка работает, **данные отказывают** | 86 % удержание, 14 % отказ |
| `--week shutdown` | с 21.06.2026 | установка стоит | 100 % отказ |

Неделя `degraded` — главная: последний лабораторный анализ старше 348 часов, анализатор
неисправен 58 % времени. Система отказывается, пока нет ни свежего анализа, ни исправного
анализатора; решает по запасной оценке, пока не работает только анализатор; и снова
отказывается, когда свежий катализатор уводит реактор ниже всего, что модель видела.

Сценарий «что если» по составу смеси и сере в сырье:

```bash
python -m scripts.blend_scenario --at "2026-07-12 14:00" --feed-sulfur 1.2 --season winter
```

## Решения, которые стоит знать заранее

**Жёсткие ограничения — фильтр, а не слагаемое.** Недопустимые варианты удаляются до
сравнения по критериям. Никакой вес не может обменять нарушение спецификации на
производительность или экономию.

**Проверка идёт по верхней границе интервала.** Вариант допустим, если `p95` прогноза серы
ниже лимита, а не если ниже точечный прогноз. Отсюда же берутся обоснованные отказы: когда
модель не уверена, интервал расширяется, множество допустимых пустеет, и система говорит
почему.

**Норма 10 мг/кг относится к товарной смеси, а режим гидроочистки проверяется по серному
бюджету резервуара** (обычно 11–12 мг/кг). В пакете нет ни телеметрии блендинга, ни точки
отбора товарного продукта, поэтому переход от промежуточного продукта к товарному — модель
смеси, и это **допущение**. Оно не является автоматически консервативным. Написано на
карточке, в `ASSUMPTIONS.md` и на слайде.

**Качество приоритетнее экономики — и в ранжировании тоже.** Помимо жёсткого фильтра есть
два правила: на признак проблемы с качеством не отвечают шагом, повышающим серу, а на
тяжесть режима — шагом, повышающим тяжесть. Веса выпуска и энергии выбраны так, что один
шаг любого рычага меняет оценку меньше, чем порог удержания: экономика разделяет близкие
варианты, но не вызывает вмешательство.

**Экономических данных в пакете нет.** Поэтому ни рублей, ни гигаджоулей: выпуск — это
расход продукта в м³/ч и т/сут, энергия — безразмерный индекс, 1.0 при типичном режиме
обучающего периода. Обе величины прозрачны и разложены на слагаемые (печь, компрессор).

**Описания тегов 24-2000 в исходном справочнике перемешаны.** Установлено в
`docs/data_audit.md`; 16 из 26 описаний противоречили и префиксу, и наблюдаемому
диапазону. 16.09.2026 организаторы прислали исправленный справочник, и набор рычагов был
пересобран по нему. Ни один неопознанный тег рычагом не является.

**Пропуски закодированы значениями-заглушками, а не пустыми ячейками.** В телеметрии нет
ни одного `NaN` и ни одного разрыва по времени; плохие показания записаны точными
значениями `307`, `0`, `251`, `252` и жёстким обрезанием на `10`. Проверка на пустое
значение не сработала бы никогда, поэтому снятие заглушек — первое преобразование в
загрузчике.

**Ни один вызов языковой модели не участвует в принятии решения.** Агенты — обычные
классы на Python. Ни одно число в рекомендации не получено и не округлено моделью.

Все допущения — в `ASSUMPTIONS.md`, с причиной для каждого. Это оцениваемый артефакт.

## Структура

```
src/neftecode/
  domain/          контракт: ProcessState, оценки агентов, рекомендация
  data/            загрузчики, построитель состояния, свежесть, синхронизация
  agents/          quality, reliability, blending, optimizer, proxies
  safety/          жёсткие ограничения, проверка качества данных
  orchestration/   цикл решения, текст карточки
  demo/            сценарии на заглушках для CLI
scripts/
  realdata.py      подготовка реальных данных: заглушки, остановы, ЛИМС/ПАК, признаки
  build_cache.py   сырые файлы → parquet
  run_real.py      мост: ProcessState из кэша, прогон недели, режим --follow
  blend_scenario.py  «что если» по смеси
  analysis/        обучение: метки, базовая модель, классификатор, опорные статистики
configs/           ограничения, веса ранжирования, спецификация смеси, рычаги
models/            коэффициенты в JSON (в git, переобучение не требуется)
ui/app.py          консоль оператора (Streamlit)
notebooks/         запуск всего пайплайна
tests/             126 тестов, включая проверку гарантии «как-если-бы»
data/raw/          пакет организаторов (вне git)
data/cache/        parquet-кэш (вне git)
artifacts/         трассы решений (вне git)
ASSUMPTIONS.md     каждое допущение с причиной
docs/data_audit.md отчёт по данным (этап 1)
```

CLI на заглушках, без реальных данных — для быстрой проверки контракта:

```bash
python -m neftecode scenarios
python -m neftecode run --scenario normal --pretty
python -m neftecode run --scenario stale_data --pretty
```
