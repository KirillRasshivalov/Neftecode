## Summary — five things a reviewer must know before approving Phase 2

1. **The 24-2000 tag reference does not describe the 24-2000 data, and this blocks a graded deliverable.** For 16 of 26 tags the description's physical type contradicts both the tag prefix and the observed values: `T11` is described as the feed mass flow but reads 295–379 (a temperature); `F19` is described as a reactor pressure but reads 128–248; `P13` is described as a sulfur quality signal but reads 3.4–4.0 (a pressure). The AVT half of the same workbook has **zero** such mismatches, so this is a defect in one table. CLAUDE.md §3 requires controllables "justified against the KIP reference" and every candidate lever falls in the broken set. Per §2 rule 2, this report stops rather than guessing (§3.3, §3.5, §8.1).
2. **The soft sensor is trainable, but its label and the online analyzer are unrelated.** LIMS carries **1,462 product-sulfur results** (`Mg.Sulfur`, мг/кг) over 1,316 days at roughly daily cadence — Phase 1's kill question is answered **yes**. But paired within ±2 h the lab and the ПАК analyzer correlate at r = **-0.003** (1,462 pairs), and no applied lag from −72 h to +72 h and no daily aggregation improves it. Of the three КИП tags the reference calls sulfur, two are demonstrably not sulfur. **LIMS is the only trustworthy sulfur measurement in the package** (§5.3, §7.4, §8.2).
3. **The data looks flawless and is not.** Zero `NaN`s, zero gaps, zero duplicate timestamps — because missing readings are written as the exact sentinel values `307`, `251`, `252` (plus `0` and a clamp at `10` on 24-2000) across most columns of both files. `D10` (crude density) is 99.99 % sentinel; `F26` is dead for a continuous ~440 days. Every routine completeness check passes and every untreated feature is poisoned. Sentinel-stripping must be the first step in the loader (§2.5, §8.3).
4. **Four things the plan assumes are simply absent**: no blending data of any kind, no product specification and no scenario list, no economic data (§7), and no reactor bed temperatures / WABT / hydrogen purity / catalyst age — so both expected controllables need proxies, and the §11 wrong-sign risk should be treated as the likely case rather than the unlucky one (§8.4). The hydrotreating and blending schematics are missing from the package (§8.7), and КИП signals have no units at all (§3.2).
5. **The Sep 12 gate is safe; Phase 3 is not.** The time axis is genuinely perfect (189,217 rows per file, exact 10-minute cadence, identical grids), the usable modelling window is ≈ 3.6 years (§6), and the contracts, loader, replay engine and stub agents depend on none of the findings above. Phase 3 does: it assumes known controllables and a known label, and today has neither (§8.8).

### 2.5 Missing data is encoded as sentinel values, not as `NaN`

**There are exactly 0 `NaN` values in the tag columns of either telemetry file.** Read together with §2.2 — a perfect time axis and no nulls — this looks like a flawless data set. It is not. Missing and bad readings are written as **exact repeated placeholder values**, and unless they are stripped they will enter every feature, every model fit, and every constraint check as if they were measurements.

Detection rule, applied blind: find every exact float value that occurs at least 100 times in at least three different columns of the same file. A physically meaningful reading does not recur to the last bit of a float in a pressure, a temperature and a flow simultaneously; a placeholder does.

#### What this means — and what it does not

It is tempting to conclude "the prefix is the real key on 24-2000" and carry on. **Do not.** The prefix gives at best a physical *category*; it never gives a location, a stream, or an equipment item, and the whole point of naming a controllable parameter is to say *which* temperature on *which* reactor. Knowing `T5` is a temperature does not tell us it is the R-201 outlet.

CLAUDE.md §2 rule 2 gives the correct instruction for exactly this case: *"If the reference does not resolve a tag, say so and stop; do not guess."* Applying that literally:

**16 of the 26 tags on unit 24-2000 are unresolved.** Their descriptions contradict both their prefix and their data, and nothing in the package breaks the tie. The unresolved set is: `T6`, `W7`, `P8`, `W10`, `T11`, `T12`, `P13`, `F14`, `T18`, `F19`, `Q20`, `Q21`, `F22`, `T23`, `P24`, `F25`.

The tags whose description, prefix and value range all agree, and which are therefore **resolved**: `F1`, `F2`, `P3`, `W4`, `T5`, `F9`, `F15`, `T16`, `F17`, `F26`.

This blocks a specific, graded deliverable. CLAUDE.md §3 requires 3–4 controllable parameters **on hydrotreating**, "each justified against the KIP reference". Of the levers §3 names — reactor inlet temperature or WABT, feed rate, hydrogen-to-feed ratio — every candidate lands in the unresolved set. §3.5 below lists the candidates anyway, with their contradictions shown, so that a single clarification from the organisers unblocks the choice immediately. **Getting that clarification is the highest-value action available before Phase 2.**

AVT is unaffected: its table is coherent, and CLAUDE.md §3 already treats AVT as context-only, so the vertical-slice gate on Sep 12 is not at risk.

### 4.2 Sampling time vs result time — only one timestamp exists

**The file carries exactly one timestamp per result, and it is unlabelled.** Each parameter occupies a column pair — an unnamed date column and a value column. There is no second date column anywhere in the sheet and no header stating whether the date is the moment the sample was taken or the moment the result was reported.

This is a hard consequence, not a footnote. CLAUDE.md §6 requires carrying the age of every analysis and forbids using data at time `t` that would not actually have been available at `t`. With one unlabelled timestamp there are two honest options:

- **(a)** treat it as the **sampling** time and require an assumed, documented reporting delay to elapse before the result may enter a feature — conservative, cannot leak;
- **(b)** treat it as the **result** time and use it immediately — leaks by exactly the lab turnaround if the assumption is wrong.

**Take (a).** The delay value is an `ASSUMPTIONS.md` entry and should be asked of the organisers. This single ambiguity is also a candidate explanation for the LIMS↔ПАК disagreement in §5.3.

The σ columns are worth a second look on their own. An analyzer that cannot move when the lab moves cannot be used to detect the event we care about.

#### Is it just a time misalignment? — lag scan

If the LIMS timestamp were the sampling time (§4.2), the two series would agree at *some* lag rather than at zero. Applied lag scanned from −72 h to +72 h in 2-hour steps, paired within ±1 h at each offset:

| Metric | Value |
|---|---|
| Lags scanned | 73 offsets from −72 h to +72 h |
| Best absolute correlation at any lag | **0.0133** (at -42 h, 1,460 pairs) |
| r at zero lag | -0.0027 |
| r of daily means | **0.0134** over 1,228 days |

**No lag rescues it.** Aggregating to daily means — which would smooth away any sub-day misalignment entirely — does not either. Whatever these two series are, they are not two measurements of the same quantity.

What it does **not** block: the message contracts, the loader, the replay engine, the orchestrator, and the stub agents — i.e. all of Phase 2 and the Sep 12 gate. ### 8.2 The label exists — but the lab and the online analyzer disagree

First, the good news, because Phase 1's kill question deserves a direct answer. LIMS carries **1,462 product-sulfur measurements** over 1,316 days at a median cadence near one per day, against a complete, gap-free 10-minute telemetry grid. **That is enough to train a lagged-feature soft sensor with a chronological split.** The soft sensor is not the blocker.

The problem is this: paired within ±2 hours, lab and online sulfur correlate at **r = -0.003** over 1,462 pairs (§5.3). Two readings described as the same stream, taken at nearly the same moment, that do not track each other. Four candidate explanations; the first two have been tested here rather than left as speculation:

1. **The LIMS timestamp is the sampling time**, so pairing it against a process-time analyzer misaligns by the lab turnaround (§4.2). **Tested and rejected.** Scanning an applied lag from −72 h to +72 h in 2-hour steps, the best absolute correlation reached is |r| = 0.0133 (at -42 h). Aggregating both sides to daily means gives r = 0.0134 over 1,228 days. There is no lag at which these two series agree.
2. **They are not the same stream.** **Tested and unresolved.** §7.4 compares the ПАК export against all three КИП tags that the reference calls sulfur: two of them are not sulfur at all, and `W7` — which carries the identical description to the ПАК export — differs from it by roughly fiftyfold and does not correlate with it. The package does not contain a second sulfur series that agrees with either.
3. **The analyzer is unreliable over this range** — which is precisely why the task statement ranks ЛИМС above ПАК. Consistent with everything above; the ПАК sulfur series never leaves a narrow band while the lab ranges over three orders of magnitude (§5.3), and it does show the §5.2 freeze and outage patterns.
4. **The package may be partly synthetic or heavily anonymised.** Stated as a hypothesis, not a finding, but the evidence is accumulating: a perfect 189,217-point time grid with zero gaps and zero nulls across 3.6 years; two "same stream" sulfur series with overlapping distributions and zero correlation at every lag; a tag reference whose 24-2000 half is systematically shuffled. If true it changes nothing about what we build — but it does mean **the demo should lean on the decision trace and the refusal logic, which are graded, and not on the sulfur model's accuracy, which may have no signal to find.**

Whatever the cause, three consequences already follow and should be treated as decided: **the model's label is LIMS**; **ПАК enters as a feature with a health flag, never as ground truth**; and **the dashboard must not display ПАК sulfur beside a predicted value as though the two were comparable**. Doing that in front of a panel of MES experts would be the single fastest way to lose the data-handling criterion.

### 8.3 Sentinel values will silently poison every feature

§2.5. There are zero `NaN`s in the telemetry and the time grid is perfect, so every routine completeness check will report a clean data set. It is not clean: bad readings are written as the exact values `307`, `251`, `252` (and `0`, and a clamp at `10`, on 24-2000), spread across most columns of both files. One AVT column (`D10`, crude density) is 99.99 % sentinel and carries no information; another (`F26`, steam to K-6) is dead for a continuous ~440 days.

This is a risk rather than a blocker only because it is now known. Untreated it would have produced a working, plausible-looking pipeline with silently corrupted lag windows and a `parameter_bounds` computed from placeholder maxima. Treat sentinel-stripping as the **first** transformation in the loader, before caching, and make `DataQualityFlags` sentinel-aware — a null check will never fire.

### 8.4 No true reaction temperature, no hydrogen purity, no catalyst age

From §3.5: the package has no per-bed reactor temperature profile, no WABT, no hydrogen purity or partial pressure, and no days-on-stream marker. CLAUDE.md §3 names "reactor inlet temperature or WABT" and "hydrogen-to-feed ratio" as the expected controllables. Neither is directly available.

Available substitutes, **all of them subject to §8.1** — every tag named here except `T5` is in the unresolved set, so these are the substitutes *if the descriptions are correct*: `T5` (R-201 gas/feed mixture **outlet** temperature) and `P8` (R-202 mixture **inlet** temperature) for reaction severity; `P24 / T11` (fresh hydrogen flow over feed mass flow) as a hydrogen-to-feed ratio; `F19` (R-202 inlet pressure) as a stand-in for hydrogen partial pressure, valid only if gas purity is roughly constant — itself unverifiable here.

**The §11 physics sanity check still applies to the substitutes.** Higher `T5` and higher `P24/T11` must reduce predicted sulfur. If the fitted signs come out wrong, the model has learned the operator's control policy rather than the process, and CLAUDE.md §11 requires reporting that immediately rather than shipping it. Given that operators raise reactor temperature *in response to* rising sulfur, the wrong sign is the **likely** outcome, not the unlucky one. Plan for the mitigation (small deltas around the operating point, monotonicity constraints) from the start rather than discovering the need for it on Sep 15.

The reliability agent loses more than the quality agent does. With no catalyst age and no bed temperatures, the severity index rests on `W10` (R-202 differential pressure — a fouling proxy), `T5`, and feed rate. That is a defensible proxy set, but it is a proxy set, and the *Надёжность* criterion is graded on "корректные допущения при неполной разметке" — i.e. on saying so plainly.

### 8.5 No units for any KIP signal

§3.2. The reference has no unit column. "Прозрачность единиц" is named explicitly in the grading table. Every KIP unit in this project will be an inference from description plus observed range. This is cheap to do and cheap to lose points on — write the table early, mark the uncertain rows as uncertain.

### 8.6 Blending is undocumented and the hard constraint is worded for the blend

§7.1. The limit is stated for commercial diesel; the package's last measured point is hydrotreated diesel. Enforcing the constraint one stage upstream is the only option, and it is *not* automatically conservative. State it, do not bury it.

### 8.7 Half the required justification does not exist

§1.2. The only process documentation is a three-page AVT schematic PDF, essentially raster, whose few extractable labels do not correspond to any tag in the КИП reference. There is no hydrotreating schematic and no blending schematic. CLAUDE.md §3 requires controllable parameters to be justified "against the KIP reference **and the process schematics**" — the second half is unavailable. Request the missing schematics; until they arrive, justification rests on the КИП descriptions alone, and the report should say so rather than implying a schematic was consulted.

### 8.8 Schedule

**The Sep 12 vertical-slice gate is not at risk.** It requires a full cycle printing an operator card with meaningless numbers; that needs the contracts, a loader, a replay loop and four stubs, none of which depend on knowing what `T11` is. Build it on schedule.

What is at risk is **Phase 3** (Sep 13–15), which assumes it can start modelling against known controllables and a known label. Right now it cannot do either. Two changes are recommended:

1. **Send the §3.3 clarification request to the organisers immediately** — it has a lead time and everything downstream of it is blocked.
2. **Move the sulfur-signal reconciliation (§7.4) into Phase 2** as named work rather than leaving it implicit in Phase 3, so that Phase 3 opens with a settled label.

If the organisers do not answer before Sep 13, the fallback is to proceed on the prefix-implied physical types, with the substitution stated in `ASSUMPTIONS.md`, in the operator card, and on the demo slide — an explicitly flagged assumption is recoverable, a silent guess is not.
